## 一、一句话结论

**8000 和 8443 不是两套服务，而是同一个 WebUI 的两个入口。**

* **8000** = 真正的业务进程（uvicorn + FastAPI，`app.main:app`），**明文 HTTP**。
* **8443** = 一个**纯 TCP/TLS 终结中继**（`scripts/tls_relay.py`，独立 systemd 单元），把 HTTPS 解密后以**明文**转给 `127.0.0.1:8000`。

8443 侧**没有任何业务逻辑**，它只是给同一个后端套了一层 TLS 外壳。两者返回的首页 HTML 逐字节相同（实测均 136140 B，标题同为「守望者系统演示」）。

```
        ┌─────────────────────────────────────────────┐
        │  浏览器                                      │
        └───┬──────────────────────┬──────────────────┘
            │ http://               │ https://
            │ (LAN IP 也可)          │ (LAN IP 也可)
            ▼                      ▼
   ┌──────────────────┐   ┌─────────────────────────────┐
   │ uvicorn          │   │ tls_relay (pid 1868)        │
   │ 0.0.0.0:8000     │   │ 0.0.0.0:8443               │
   │ 明文 HTTP        │   │ TLS 1.3 终结 + 字节透传      │
   │ (真正的业务)      │◀──│ 注入 X-Forwarded-Proto:https │
   └──────────────────┘   └─────────────────────────────┘
            ▲
            │ 同一进程内
   ┌────────┴──────────────────────────────────────────┐
   │ compute_worker 子进程 × 3（qwen3.5-vl-4b /        │
   │ DepthAnythingV3 × 2）—— 只属于 8000 这条链路        │
   └───────────────────────────────────────────────────┘
```

## 二、进程与 systemd 单元对照

| 项 | **8000** | **8443** |
|---|---|---|
| 主进程 | `uvicorn app.main:app`（pid **7016**） | `python -u scripts/tls_relay.py`（pid **1868**） |
| systemd 单元 | `wdnwebui.service` | `wdnwebui-tls-relay.service` |
| 运行用户 | `root` | `rockchip`（**降权**，relay 只需读证书 + 连本机 8000） |
| 监听地址 | `0.0.0.0:8000` | `0.0.0.0:8443` |
| 常驻内存 | **2.4 G**（含 3 个 compute_worker 子进程） | **44.8 M**（纯转发，无模型） |
| 启动时间 | 2026-11-13 01:22（3 天前） | 2026-04-27 19:48（**已稳定运行 6 个月 19 天**） |
| 重启策略 | `Restart=on-failure` / `RestartSec=5` | 同上，**外加 `RestartPreventExitStatus=1`** |
| 依赖关系 | — | `After=wdnwebui.service` |
| 崩溃后果 | 全站不可用 + **连带杀掉全部 compute_worker**（systemd `KillMode=control-group`） | 仅 HTTPS 入口失效，**8000 明文照常可用** |

`RestartPreventExitStatus=1` 的含义：relay 启动时若**缺证书**会主动 `return 1` 退出，systemd **不会**把它反复拉起 —— 这是刻意的「宁可不提供 HTTPS，也不静默降级成明文」。

## 三、请求链路的关键机制

### 3.1 `X-Forwarded-Proto` 注入（relay 侧）

TLS 在 relay 进程里终结，后端收到的是明文 HTTP，它会以为自己是 `http://`，于是自己生成的绝对 URL 全带 `http://`。最要命的是 FastAPI 尾斜杠 307 重定向：

```
GET /api/tts → 307 Location: http://<host>/api/tts/
```

https 页面拿到 `http://` 的重定向目标 → 浏览器按 **mixed content** 拦掉 → `fetch()` reject 成 `TypeError: Failed to fetch`。

所以 relay 给**每个**请求头注入 `X-Forwarded-Proto: https`（`scripts/tls_relay.py:165-168`）。注意「每个」：浏览器会复用 keep-alive 连接，只注入第一个的话，**同一条连接上的第二个请求 scheme 又退回 http**（实测踩过）。

同时 relay 会**摘掉**客户端自带的 `x-forwarded-proto` / `x-forwarded-for`，避免叠成 `"https, http"`。

### 3.2 `scope["scheme"]` 落地（后端侧）

`app/core/forwarded.py::XForwardedProtoMiddleware`（挂载于 `app/main.py:188`）把该头落到 `scope["scheme"]`，WebSocket 相应映射成 `ws` / `wss`。

**安全边界**：只信任回环对端（`127.0.0.1` / `::1` / `::ffff:127.0.0.1`）。因为 8000 端口是对整个局域网开放的，任意客户端都能自己塞一个 `X-Forwarded-Proto` 进来 —— 非回环塞了不认（与 uvicorn 默认口径一致）。

该中间件不依赖 uvicorn 的 `ProxyHeadersMiddleware`（那个只信 127.0.0.1，且**可以被 `--no-proxy-headers` 关掉**）—— 那是 CLI 默认值不是契约，关掉了 scheme 会静默退回 `http://`，症状一模一样。

### 3.3 连接复用（实测）

relay 采用「**一个客户端连接 ↔ 一条到 8000 的连接**」的映射（`scripts/tls_relay.py:202-225`），不是每请求新建连接。

实测：同一 keep-alive 连接连发 3 个请求走 8443 → `num_connects=1`；直连 8000 连发 3 个 → `num_connects=0`（复用已有连接）。**keep-alive 在两条链路上都成立。**

### 3.4 实测证据：重定向 Location 正确区分

```
$ curl -sSI http://127.0.0.1:8000/api/tts | grep -i location
location: http://127.0.0.1:8000/api/tts/

$ curl -sSI --cacert ca.pem https://127.0.0.1:8443/api/tts | grep -i location
location: https://127.0.0.1:8443/api/tts/
```

⇒ `X-Forwarded-Proto` 链路**工作正常**。

## 四、协议能力对照

| 能力 | **8000（HTTP）** | **8443（HTTPS）** |
|---|---|---|
| HTTP | ✅ 明文 | ✅ TLS 1.3 / `TLS_AES_256_GCM_SHA384` |
| WebSocket | `ws://` | `wss://`（relay 对 Upgrade 请求**原样透传**，101 之后是隧道字节不再按 HTTP 解析） |
| HTTP/2 | ✅（uvicorn h11 不支持，实际为 HTTP/1.1） | ❌ **ALPN 协商失败，退回 HTTP/1.1**（relay 是裸字节转发，不参与 ALPN） |
| 浏览器**安全上下文** | 仅 `http://localhost` / `http://127.0.0.1` 是 | ✅ **任意 LAN IP 都是** |
| `navigator.mediaDevices` | LAN IP 访问时 **undefined** | ✅ 存在 |
| 浏览器麦克风（实时 ASR） | ❌ **点「开始录音」静默失败** | ✅ 可用 |
| 传输加密 | ❌ 明文（网口上裸奔） | ✅ TLS |
| 访问控制 | ❌ **无鉴权** | ❌ **同样无鉴权** |

> **两个端口都没有任何认证**（`app/main.py` 里只有 `XForwardedProtoMiddleware` 和 `GZipMiddleware`，没有 auth / CORS 中间件）。TLS 解决的是「安全上下文 + 传输加密」，**不解决访问控制**。

### 浏览器麦克风为什么必须走 8443

浏览器只在**安全上下文**（https，或 http://localhost/127.0.0.1）里暴露 `navigator.mediaDevices`。明文 `http://172.16.9.65:8000` 里它是 `undefined` —— 点「开始实时识别」什么都不会发生，且前端会主动提示改用 `https://…:8443`（回归用例 U9 / U10）。

### 5.1 当前证书（实测 `openssl x509`）

```
subject = CN = 172.16.9.65, O = wdnwebui
issuer  = CN = wdnwebui Local CA, O = wdnwebui
validity: Nov  8 07:49:53 2026 GMT  →  Nov  5 07:49:53 2036 GMT  (10 年)
SAN: IP Address:172.16.9.65, DNS:debian, DNS:localhost, IP Address:127.0.0.1
```

### 5.2 私有 CA 结构（`scripts/gen_tls_ca.sh`）

```
/home/rockchip/.config/wdnwebui/tls/
├── ca.pem        ← CA 根证书（自签）—— **发给客户端的就是这个**
├── ca-key.pem    ← CA 私钥（只在签发时用，可挪走离线保管）
├── cert.pem      ← 服务端叶子证书（由 CA 签发）—— tls_relay.py 加载它
└── key.pem       ← 服务端私钥
```

**为什么要 CA 而不是自签叶子**：自签叶子只有两条路 —— 每次访问点「高级 → 继续前往」，或手工装进信任库（且每次续签/换 IP 都要重新分发一次，部分浏览器处理不一致）。用私有 CA：客户端只装**一个**根证书（永久有效），叶子可以随时续签/换 IP 而**不用再动客户端**。

### 5.3 本机信任状态

| 位置 | 内容 |
|---|---|
| `/usr/local/share/ca-certificates/wdnwebui-local-ca.crt` | CA 根已进系统信任库（`update-ca-certificates` 跑过） |
| `~/.pki/nssdb` | CA 根已进 NSS 库（本机 Chromium 认） |

实测**不加** `--cacert` / `-k` 直连 `https://172.16.9.65:8443/` → `code=200 verify=0` ✅。

### 5.4 客户端信任（局域网其他机器）

* **Chrome/Edge (Linux)**：Chrome 读 NSS 用户库，**不读** `/etc/ssl/certs` → `certutil -A -d sql:$HOME/.pki/nssdb -t "C,," -n "wdnwebui Local CA" -i ca.pem`
* **Chrome/Edge (Windows)**：双击 `ca.pem` → 本地计算机 → 受信任的根证书颁发机构
* **macOS**：钥匙串访问 → 拖进「系统」钥匙串 → 「始终信任」
* **Firefox**：证书 → 颁发机构 → 导入 → 勾「信任此 CA 来标识网站」
* **Android**：安全 → 加密与凭据 → 安装证书 → CA 证书
* **iOS**：装成描述文件 → 通用 → 关于本机 → 证书信任设置 → **手动打开信任开关**（iOS 13+ 对自建 CA 的额外要求）

⚠️ **CA 私钥泄露 = 任何人都能伪造一个本板认可的证书。** 签发完建议把 `ca-key.pem` 挪到离线介质。

## 七、性能实测

### 7.1 本机单次首页（本次实测）

| 路径 | 状态 | 耗时 | 字节 |
|---|---|---|---|
| `http://127.0.0.1:8000/` | 200 | **61.6 ms** | 136140 |
| `https://127.0.0.1:8443/` | 200（verify=0） | **58.2 ms** | 136140 |

单次请求两者基本持平（relay 只多一次本机 loopback 握手，被 TLS 握手开销抵消）。

### 7.2 并发场景（`docs/WEB_DELIVERY_PERFORMANCE.md:38`）

| 场景 | 耗时 |
|---|---|
| 16 并发请求 × 8 个路径，明文（8000） | **90 ms** |
| 16 并发请求 × 8 个路径，TLS（8443） | **193 ms** |

⇒ **TLS 路径在并发下约为明文的 2 倍**。这是 TLS 握手 + 加密开销叠加的结果，单请求看不出来，批量并发才显著。

### 7.3 页面字节量（与端口无关）

首屏真实过线字节修复后：**冷加载 784 KB / 热加载 190 KB**（gzip + 缓存，修复前 4.29 MB）。这部分走哪个端口都一样。

## 八、已知限制与风险

1. **relay 无超时、无限流、无背压控制**。后端挂掉时只打一行 `连不上后端 127.0.0.1:8000 — [Errno 111] Connect call failed` 并关闭客户端连接。实测 2026-11-13 01:22 uvicorn 重启那几秒，relay 日志刷的正是这个（说明 relay 本身活着，只是后端在重启窗口内不在）。

2. **chunked 请求体退化为「一连接一请求」**。relay 遇到 `Transfer-Encoding: chunked` 会主动加 `Connection: close`（`scripts/tls_relay.py:169-172`）——宁可少复用，也不能把二进制请求体（音色 WAV 上传）的帧边界算错。

3. **请求头 > 64 KB 时放弃注入 `X-Forwarded-Proto`**（`MAX_HEAD_BYTES`）→ scheme 退回 `http://` → 307 Location 写成 `http://` → https 页面按 mixed content 拦掉。极少见，但触发条件是「超长 header」。

4. **HTTP/2 不可用**。relay 不参与 ALPN 协商，8443 一律 HTTP/1.1。8000 侧 uvicorn 本身也是 HTTP/1.1，所以**没有功能差异**。

5. **证书绑定当前 IP**。换 IP 需重签叶子：`bash scripts/gen_tls_ca.sh <新IP> --force-leaf && sudo systemctl restart wdnwebui-tls-relay.service`。CA 根不变 → **客户端不用重装**。

6. **8443 与 8000 的 WebSocket 断开语义一致**。`scripts/verify_ws_disconnect.py` 对 4 个端点 × 3 种断开方式（正常关闭 / 客户端 SIGKILL / 经 relay）都验证过能及时收尾 —— **relay 不是关停链路上的元凶**。

7. **两个端口都无鉴权**。8443 提供的是加密与安全上下文，**不是访问控制**。若要限制谁能访问，需要在 relay 层加 IP 白名单或在应用层加鉴权 —— 当前均未实现。

8. **relay 单元的 `After=wdnwebui.service` 只是排序，不是强依赖**。两者都是 `Restart=on-failure` 独立重启；relay 不会因为后端重启而重启（这正是它能扛住后端重启窗口的原因）。

## 九、使用建议

| 场景 | 推荐入口 | 理由 |
|---|---|---|
| 本机调试 / 回归脚本 | **8000** | 无需处理证书，延迟略低 |
| 板载内部调用（麦克风 agent 等） | **8000** | 同上，且不受 relay 故障影响 |
| **局域网其他机器 + 浏览器麦克风 / 实时 ASR** | **8443（必须）** | `http://<LAN-IP>:8000` 下 `navigator.mediaDevices` 是 `undefined`，点录音静默失败 |
| 局域网其他机器 + 不用麦克风 | 8443 更保险 | 传输加密；代价是并发下约 2× 延迟 |
| 对外/不可信网络 | **8443，且应额外加访问控制** | 当前无鉴权 |

**一句话**：能用 8000 就用 8000（快、简单、无证书依赖）；**一旦要用浏览器麦克风，就必须走 8443**。

## 十、验证与排查命令

```bash
CA=/home/rockchip/.config/wdnwebui/tls/ca.pem

# 1) 两个单元都在跑
systemctl status wdnwebui.service wdnwebui-tls-relay.service --no-pager

# 2) 端口在监听
ss -ltnp | grep -E '8000|8443'

# 3) 两条链路都通
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/
curl -sS --cacert $CA -o /dev/null -w "%{http_code} verify=%{ssl_verify_result}\n" https://127.0.0.1:8443/

# 4) scheme 传递正确（两个 Location 必须各自带 http / https）
curl -sSI http://127.0.0.1:8000/api/tts    | grep -i location
curl -sSI --cacert $CA https://127.0.0.1:8443/api/tts | grep -i location

# 5) 回归脚本
python -m scripts.verify_tls_scheme        # 8/8

# 6) 浏览器侧验证（两条路径覆盖 88 / 72 条断言）
WDNWEBUI_BASE=https://172.16.9.65:8443 python scripts/verify_asr_wizard.py   # 88 通过 / 0 失败
WDNWEBUI_BASE=http://172.16.9.65:8000  python scripts/verify_asr_wizard.py   # 72 通过 / 0 失败（16 条浏览器麦用例按设计跳过）

# 7) 证书链
openssl verify -CAfile $CA /home/rockchip/.config/wdnwebui/tls/cert.pem
```
