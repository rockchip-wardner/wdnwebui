# 同传链路耗时分析报告（板端实测）

> 采集时间：2026-11-26 12:20 ~ 12:57（板端运行中会话）
> 采集方式：直接读运行中的服务接口快照 —— `GET /api/tts/queue/status`、
> `GET /api/qwen3-asr/interp/status`、`GET /api/qwen3-asr/rounds`、
> `GET /api/qwen3-asr/translate/status`
> 样本：真实会话「圆桌派 第八季 EP01」（含音轨的中文谈话视频，98 分钟）

---

## 0. 摘要（一句话结论）

**四环节里只有 TTS 合成是瓶颈，其余三个都大幅富余。**

| 环节 | 需求 | 实测产能 | 余量 | 判定 |
|---|---|---|---|---|
| ASR 转写 | 0.291 句/s | **2.04 句/s** | **7.0×** | ✅ 富余 |
| 翻译（MT） | 0.291 句/s | **1.61 句/s** | **5.5×** | ✅ 富余 |
| **TTS 合成** | 0.291 句/s | **0.261 句/s** | **0.90×** | ❌ **缺 ~10%** |
| 喇叭播放 | 1.0× 音频 | 1.025×（1:1 无损） | — | ✅ 不是瓶颈 |

⇒ **TTS 合成缺的那 ~10%，就是"播报比字幕慢"的全部来源**：
可听滞后 `a_lag` 在实测区块里从 **7.68 s 单调涨到 23.46 s**（漂移率 **12.1%/s**）。

## 2. 四环节逐段耗时

### 2.1 ASR 转写

| 指标 | 实测 |
|---|---|
| 实时比 | **2.04×**（1 秒素材 2.04 秒转完） |
| 本轮轮次 / 覆盖 | 5624 轮 / 5623 s 音频（每轮覆盖 1.00 s） |
| 单轮墙钟 | **0.49 s** |
| 领先播放头 | **5461 s**（ASR 已到 5868 s，播放头在 406 s） |

⇒ **视频源下 ASR 是"离线式快进"的**：转写速度远快于播放头，字幕不是被 ASR 拖住的。
（文档里"ASR ≈0.6× 实时"是**实时麦流**的口径，不适用于本路径。）

### 2.2 翻译（MT）

| 指标 | 实测 |
|---|---|
| 等模型就绪 `wait_mt` | **0.000 s**（模型常驻） |
| 单句推理 `infer` | p50 **0.62 s** / p90 1.12 s / max 1.39 s |
| 翻译产能 | **1.61 句/s**（需求 0.291 ⇒ 富余 5.5×） |
| 接口自报 `avg_latency_ms` | 570.4 ms |
| 失败率 | 163 / 3287 = **5.0%** |

⇒ 翻译**从不是瓶颈**。

### 2.3 TTS 合成 ← **瓶颈在这里**

| 阶段 | p50 | p90 | max |
|---|---|---|---|
| 提交 → 开始合成（**排队**） | **25.97 s** | **63.01 s** | **66.13 s** |
| 开始合成 → 首帧 PCM（**首窗**） | **2.03 s** | 2.09 s | 3.06 s |
| 提交 → 出声（`pipe_lat`） | **37.51 s** | 65.05 s | 68.18 s |
| 开始合成 → 出声（`synth_lat`） | 2.07 s | 14.70 s | 23.12 s |
| 出声 → 播完 | 3.01 s | 7.47 s | 14.27 s |

**单句成本拆解**（前台独占区间 seq163~271，38 句）：

```
每句占用墙钟   4.06 s
每句产出音频   3.50 s
每句固定开销   0.56 s   ← 首窗 2.03 s 与上一句的播放重叠，净摊 0.56 s
```

**两种速率口径（都要看）**：

| 口径 | 值 | 含义 |
|---|---|---|
| `rate`（**边际**速率，EMA） | **0.998×** | 出了首窗之后，模型本身**能跑满 1.0×** |
| `sustain_rate`（**整体**速率，EMA） | **0.913×** | 把每句的首窗摊进去 ⇒ **只有 0.91×** |

⇒ **模型本身不是瓶颈，"每句一次首窗"才是。**

**缺口推导**（按源话 1 秒 = 0.291 句算）：

```
每源秒需要的音频产量   = 0.291 句 × 3.50 s/句 = 1.019 s
每源秒需要的线程时间   = 1.019 (音频) + 0.291×0.56 (首窗净摊) = 1.182 s
线程每秒只能给          = 1.000 s
⇒ 播报轨只能推进       = 1.000 / 1.182 = 0.85×  实时  ⇒ 每秒落后 ~15%
（用队列自报 0.913× 口径算 ⇒ 落后 ~11%；实测漂移 12.1%/s，落在两者之间）
```

**排队为什么会涨到 66 秒**：前台每 0.2 s 提交一句（`_gate_worker_prefetch` 一次只放一句），
提交速率 **0.45 句/s** > 合成速率 **0.26 句/s** ⇒ 队列单调增长 ⇒ 每句的等待线性拉长。

### 2.4 喇叭播放（aplay → ALSA → 板载 codec）

| 指标 | 实测 |
|---|---|
| 实际出声时长 / 合成音频时长 | **p50 = 1.025** ⇒ 播放端 **1:1，无二次伸缩** |
| 首帧 PCM → 播完 | p50 3.01 s（= 音频本身长度） |
| 句间空隙 `gap` | 均值 **0.33 s** / p90 0.69 s / max 5.33 s |
| 断音比 | 19.8 s / 200.7 s = **9.9%** |
| aplay 输出峰值 | `last_out_peak=0.045`（raw 0.2668）⇒ **声音确实送到板载 codec** |
| 变速 | sox `tempo` **只作用于播放**，不影响合成（`tts_bridge.py:76`） |

⇒ **播放环节零额外延迟、零损耗**，唯一代价是句间 0.33 s 的管道空隙（断音）。

## 3. 端到端时间预算

### 3.1 拖动进度条后的"第一声"瀑布（实测，实测值 = 真实时间戳差）

| 相对 seek | 事件 | 耗时来源 |
|---|---|---|
| +0.0 s | 用户拖到 244.75 s | — |
| +2.8 s | ASR 转写到源话 250.41 s | 5.66 s 素材 ÷ 2.04× |
| +3.4 s | MT 译完 | 推理 0.62 s |
| +4.7 s | 放行器放行 | 播放头到达 `句首 − lead(1.0 s)` |
| +6.6 s | 提交进 TTS 队列 | 实测 `t_submit` |
| +9.9 s | 合成线程开始合成 | **排队 3.3 s** |
| +12.0 s | 首帧 PCM | **首窗 2.03 s** |
| **+12.1 s** | **出声** | ⇒ 可听滞后 **7.68 s** |

⇒ **拖动后要等 12.1 秒才出第一声**，其中 **5.3 s 是 TTS 侧**（排队 + 首窗）。

### 3.2 稳态漂移（实测 seq163→271）

```
源话跨度   250.41 → 380.84 s  = 130.43 s（38 句）
译文音频总长                    = 133.03 s
⇒ 长度比 k                       = 1.020（译文只长 2.0%）
可听滞后 a_lag                   = 7.68 → 23.46 s（+15.78 s）
漂移率                          = 12.1% / 秒
```

⇒ **注意**：k 只有 **1.02**，**不是**文档里估的 1.15~1.30。
漂移**不是长度比造成的**，而是 **TTS 合成吞吐 0.91× < 需求 1.02×** 造成的。

⚠️ 投影：若不干预，按 12.1%/s 漂，播到素材结尾（5868 s）时累计落后 **≈ 680 秒（11 分钟）**。

## 4. 产能账：结构性冲突

单卡单 TTS 实例（`tts_instances=1`）要同时干两件事：

| 用途 | 需要的线程产能 |
|---|---|
| 前台播报轨（跟住字幕） | k × 1.0× = **1.02×** |
| 后台预热（整段 98 分钟进缓存） | **≈ 1.0×** |
| **合计需求** | **≈ 2.02×** |
| **实际可用** | **0.91×** |
| **缺口** | **≈ 2.2×** |

⇒ **"预合成整段" 与 "跟播同步" 在单实例下互斥。**
实测印证：前台跑起来后，后台积压从 0 涨到 **693** 且**不再下降**（前台优先 ⇒ 后台饿死），
缓存停在 618 条。

⇒ 只有一个 TTS 实例时，只能三选一：

| 方案 | 跟播同步 | 拖动即命中 | 代价 |
|---|---|---|---|
| ① 只跟播（放弃预热） | ✅ | ❌ 拖到没合成的位置要现场合成 ~3 s | 拖动后有等待 |
| ② 只预热（放弃跟播） | ❌ 必然落后 | ✅ | 越播越慢 |
| ③ **上第二个 TTS 实例**（跨卡聚合 **2.07×**） | ✅ | ✅ | 占第二张卡 |

## 5. 三个结论

**① 「跟不上就不念」不是产能问题，是一条过期的策略。**
它写在 `interp.py:367-387`，理由是"过期句会占住串行合成线程 ~8 s，拖死后面新鲜的句"。
在预合成架构下这条理由已失效：后台早已把音频合成进缓存，提交过期句的边际成本 ≈ 0。
现在这条规则的真实效果是**那句译文整场不出声**（除非源播完时全放）。

**② 面板上「2941 句已过期未念」是错的。**
`_stale_skipped` 在 `_foreground_candidates()` 里自增，而该函数每 **0.2 s** 被调一次、
每次重扫整个 `_pending`，而过期句**永远留在 `_pending` 里** ⇒ 同一句被反复计数。
计数器还**从不清零**（seek 也不重置）。
实测复现：1 句过期 → 5 次 tick 后计数器 = **5**。
本次会话现场值 **51721** ⇒ 真实过期句数是个位数。

**③ 要真正做到"播报与源语音同等节奏"，必须同时解决三件事**：

| # | 事项 | 依据 |
|---|---|---|
| a | **拆开"过期"的两种成因**：用户 seek 跳过 ⇒ 丢弃（对）；译文自己落后 ⇒ 现在补播（现在错，是静音） | 源语音在那段也没播 ⇒ 丢弃是对的 |
| b | **补上 TTS 的 ~10% 缺口**：边际速率 0.998× vs 整体 0.913× ⇒ 差在**每句首窗 2.03 s** ⇒ 合并 2~3 句摊薄首窗，或上第二实例 | §2.3 / §4 |
| c | **槽位内对齐（tempo）**：k=1.02 ⇒ 差 2%；但中→日/中→德等 k 可达 1.05~1.30 ⇒ 需要"按槽位算 tempo"而不是全局钉死 1.0 | §3.2 |

> ⚠️ **tempo 只能治标不能治本**：`sox tempo` 只作用于播放、不影响合成 ⇒
> 它能让已经落后的播报**追回来**（1.15× ⇒ 每秒追 0.15 s），但**不能提高合成吞吐**。
> 稳态要跟上，必须靠 (b)。

## 6. 建议（按性价比排序）

| # | 改动 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | 修过期计数器（按 index 去重 + seek 重置 + 面板改成"过期句数/其中 seek 跳过"） | 面板说实话，排障不再被带偏 | 极低 |
| 2 | "过期"策略按成因拆开（seek 跳过 vs 自身滞后补播） | 消灭"内容凭空消失" | 中 |
| 3 | 允许预合成模式用 tempo（按积压自动 1.0→1.15），并把"追滞后"纳入变速决策 | 落后 20 s 时 ~2 分钟追平 | 低 |
| 4 | TTS 作业支持**按源位置合并**（合并后仍记位置区间）⇒ 摊薄首窗 0.56 s/句 | 合成吞吐 0.86~0.91 → ~0.98×，**填平那 10~15%** | 中高（位置映射要重做） |
| 5 | 第二个 TTS 实例（跨卡 2.07×） | 预热 + 跟播同时成立 | 高（占卡） |
